# 首頁與典藏題目搜尋

首頁搜尋所有未典藏的題庫，典藏庫搜尋 `_Archive_` 開頭的題庫。即使已進入某個科目，題目搜尋仍涵蓋該區全部題庫；上方科目／題庫名稱篩選維持目前列表的範圍。

搜尋詞只要是題目或任一選項文字的連續片段，就列出該題。題幹與每個選項分別核對，不會把不同選項接起來產生誤命中。答案、詳解、出處及題庫名稱不參與題目比對；題庫名稱仍可透過原有列表篩選找到。

搜尋忽略英文大小寫、全半形差異及連續空白，使用 Unicode NFKC 正規化。這適用於搜尋用途；顯示內容仍使用原文，避免改寫公式或選項。[MDN 的正規化說明](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/String/normalize)

## 結果呈現

- 卡片列出科目、題庫、第幾題及原始出處（若有），完整顯示題目與全部選項。
- 標示「符合題目」或符合的選項字母，並在一般文字上標記搜尋詞。公式先排版再標記，保留數學排版。
- 答案與詳解使用原生 `details`，每次搜尋預設收合；展開時才建立內容並處理公式。沒有詳解時顯示資料狀態。
- 題幹命中優先，其次依題庫名稱及原始題序排列。相同題幹在不同來源／題序仍各自列出。
- 每次顯示 20 題，可持續按「顯示更多題目」查看全部結果，沒有搜尋數量上限。
- 「練習此題」使用既有自訂學習模式。返回首頁保留搜尋詞與原本科目，不覆寫原題庫測驗進度。
- 手機使用同一張單欄卡片；圖片、表格、程式碼與顯示公式限制在卡片寬度內。

## 索引選擇與研究

採用**字元 1／2／3-gram 倒排索引，加上逐欄連續片段核對**，於登入帳戶的瀏覽器記憶體中建立。這是本專案的實作，沒有引入 PostgreSQL 或外部搜尋服務。

[Stanford 的資訊檢索教材](https://nlp.stanford.edu/IR-book/html/htmledition/k-gram-indexes-for-wildcard-queries-1.html)說明 k-gram 倒排清單及候選核對：索引中的片段都出現，仍不代表原查詢真的連續出現，因此必須再檢查原文。本實作直接把字元片段對應到題目 ID，並在題目或單一選項上執行 `includes` 核對。

[PostgreSQL 的 trigram 索引](https://www.postgresql.org/docs/current/pgtrgm.html)也支援非開頭限定的片段查詢，但沒有足夠 trigram 的短查詢可能退化成掃描。本專案額外建立 unigram／bigram 清單，讓單一中文字與兩字查詢同樣可以查索引；此外保留標點與數字，便於搜尋 `pH < 6.5` 等內容。

| 方法 | 與需求的適配性 | 決定 |
| --- | --- | --- |
| 逐題 `includes` 掃描 | 精確且實作簡單；每次查詢仍需檢查全部文字 | 作為正確性測試基準 |
| 單詞倒排索引／BM25 | 適合詞彙相關性排序；任意中文片段、英文單詞中段仍需額外處理 | 不作為本次主要索引 |
| Trie／前綴索引 | 適合搜尋開頭；若要任意中段，需增加後綴結構 | 不採用 |
| 模糊搜尋／編輯距離 | 可找拼字近似，但會列出沒有實際包含搜尋詞的題目 | 不符合本次精確包含規則 |
| 字元 n-gram 倒排索引 | 不依賴中文斷詞，支援中英片段、數字與標點；需要記憶體與初次建置 | 採用 |

Firebase Realtime Database 提供排序、相等及範圍查詢；本專案依官方列出的查詢能力，判斷目前的題庫結構需要額外的搜尋索引來處理任意文字片段。[Firebase 查詢文件](https://firebase.google.com/docs/database/web/lists-of-data)

### 資料結構與查詢流程

1. 使用既有安全 Markdown 輸出取得題幹與選項的文字；不把 HTML 標籤、連結網址或詳解加入索引。
2. 每個欄位正規化，再切出 1、2、3 字元片段。同一題的重複片段只存一次。
3. `Map<gram, number[]>` 保存遞增數字 ID 的倒排清單。題目另外保存來源、原題序及正規化欄位，不持有每題的重複 gram 集合。
4. 查詢長度為 1 或 2 字元時使用相對應清單，其他查詢使用 3 字元清單。
5. 先遍歷最短的候選清單，再以二分搜尋確認候選存在於其餘清單。從最少候選開始是資訊檢索常見的查詢最佳化。[Stanford 的布林查詢說明](https://nlp.stanford.edu/IR-book/html/htmledition/processing-boolean-queries-1.html)
6. 候選題目逐欄核對完整搜尋詞，再套用首頁／典藏範圍及排序。

設全文字元數為 `L`，建置的時間與空間為 `O(L)`（最多三種片段長度）。查詢會先切出 `G` 個片段，遍歷最短清單的 `C` 個候選，對其他清單做二分查找，再核對候選欄位與排序。沒有宣稱常數時間；常見單字、單一中文字或幾乎所有題目都包含的詞，仍可能產生大量候選。

### 載入與更新

- 尚未輸入搜尋詞時，不為搜尋下載題庫內容；輸入後等待 150 ms，中文輸入法組字結束再搜尋。
- 首次搜尋只讀取該區題庫，最多同時讀四份，並顯示讀取進度。首頁不為搜尋預載典藏內容。
- 每份題庫建好索引後讓出一次事件迴圈，避免多份題庫連續建置阻塞介面。同一區後續查詢重用已成功載入的題庫。
- 使用現有 `readBank` 的離線快取；權限拒絕不以舊快取繞過。索引不另外持久化。
- 載入失敗會顯示「搜尋結果尚未完整」，可重試未成功的題庫。
- 登出／切換帳戶會清除搜尋索引與卡片；更新目錄（包含新增、重新命名、典藏、還原）會清除索引，再依目前範圍建立。頁面、帳戶或目錄版本改變後，延遲回應不會加入新的索引或覆蓋當前結果。
- 索引大小隨內容量成長，單份大型題庫的解析與建置仍在主執行緒。若未來首次下載、建置時間或裝置記憶體成為瓶頸，應另評估 Worker 或伺服器索引；目前採用無額外服務、沿用既有讀取權限的方案。

## 驗證與效能

單元測試將混合中文、英文、標點、全形及補充平面字元的索引結果，與逐題掃描結果比較，另涵蓋封存隔離、欄位邊界、重複題幹、內容替換、載入重用、重試、四份讀取上限及帳戶／目錄更新時的延遲回應。

瀏覽器測試使用隔離 Firebase 模組，涵蓋選項命中、詳解收合、分批結果、Markdown 安全輸出、跨科目搜尋、單題練習與返回、桌面／手機、權限拒絕後重試、典藏還原及登出。正式 Firebase 資料不參與測試。

```sh
node --test tests/search.test.js
CHROME_PATH='/Applications/Google Chrome.app/Contents/MacOS/Google Chrome' node tests/search-browser.mjs
node --expose-gc scripts/benchmark-search.mjs
```

2026-10-04 本機 Node.js 22、10,000 題混合中英合成資料的示例：索引建置約 406 ms，GC 後額外 heap 約 33.3 MiB；不包含網路下載、Markdown 解析或卡片排版。下表為每種查詢 30 次的平均，掃描基準已預先正規化，且沒有結果排序，較有利於掃描。

| 查詢 | 命中 | 索引查詢（含排序） | 預正規化掃描 |
| --- | ---: | ---: | ---: |
| 受體 | 3,334 | 0.844 ms | 0.302 ms |
| CHOLINE | 10,000 | 2.556 ms | 0.321 ms |
| pH < 6.5 | 10,000 | 2.468 ms | 0.399 ms |
| 不存在的詞 | 0 | 0.001 ms | 0.315 ms |
| case 0007pr | 1 | 0.003 ms | 0.602 ms |

這份合成資料顯示，稀有或不存在的片段適合倒排索引；大量命中時，候選查找、核對及排序反而可能比簡單掃描慢。因此選擇索引是為了可重用的中英片段檢索與候選縮小，不把效能提升視為每種查詢的保證。實際使用體感也取決於初次 Firebase 下載與題庫大小。
